# queue-identity：多来源客户主数据历史身份解析 v1

`queue-identity` 面向服务中心的 CRM、预约和热线导出，提供**历史时点的统一
客户视图**：静态客户记录带来源键，人工确认的同人关联带 `[from_tick,
to_tick)` 有效期，数据人员按时点查询任一记录所在身份分量的规范代表、成
员数、来源冲突隔离状态与逐字段主数据血缘。仅用 Python 标准库，不连接网
络，也不读写 queue-planner 的 SQLite 数据库或其他命令的报告。

```sh
python -m queue_identity.cli --source IDENTITY.json --output REPORT.json
# 安装后等价入口
queue-identity --source IDENTITY.json --output REPORT.json
```

API：

* `queue_identity.cli.run(source_path)`：读取并校验源文件，返回报告字典
  （含 `schema_version`、`source_sha256`）；
* `queue_identity.model.resolve(document)`：接收**已解析**的 JSON 文档，
  返回 `{"queries": [...]}`（不含摘要，便于测试）。每个查询行只由该查
  询时点的有效关联决定，与查询在输入中的顺序无关。

CLI 入口名 `queue-identity` 已在 `pyproject.toml` 注册。

## 安全边界（与既有命令共用）

* 输入、输出都是严格 JSON：重复键、NaN/Infinity、未定义字段一律拒绝。
  输入有 8 MB **字节**上限（超限读取即停，不整份载入）。
* 输出先写同目录临时文件再 `os.replace` 原子替换，写入失败不会留下半份
  新报告。输入错误、校验失败或计算失败退出码 **2** 并**保留旧报告**与
  源文件；成功退出 **0**。
* 输入与输出不得是同一路径（按 `Path.resolve()` 比较）；输出是符号链接、
  或与输入共享 inode（硬链接/目录符号链接别名）时拒绝。
* `source_sha256` 按输入**原字节**计算，是唯一允许随原字节重排变化的
  报告字段；其余所有字段只由输入语义决定，数组重排不会改变报告。

## 源文档结构

顶层**恰含** `sources, records, links, queries`。四个数组都允许为空
（`sources` 除外），但整份源中的全部结构和引用仍被完整校验——未被判
任何查询触及的记录、关联也不能跳过校验。

### sources（1..64 项）

每项恰含 `id, priority`：

* `id` 沿用本仓 `ident` 规则（非空、无首尾空白、≤128 字符、无控制字
  符），在来源侧唯一；
* `priority` 为 0..10^9 的整数（拒绝 bool、浮点、字符串）。**数值越
  小越优先**；不同来源允许相同优先级，并列时按 `source`、再按 `key`
  的 Python 字符串顺序判胜。

### records（0..10000 项）

每项恰含 `source, key, display_name, email, phone`：

* `source` 引用已声明的来源 id；`key` 沿用 `ident` 规则；`(source,
  key)` 联合唯一（同一 `key` 出现在不同来源是不同记录）。
* `display_name, email, phone` 各为 `null` 或通过 `ident` 校验的字符
  串，**保持原值**：不修剪、不大小写折叠、不格式化、不做模糊匹配。
* 客户键始终保留 `(source, key)` 两个独立分量，绝不拼接成字符串冒充
  身份；带分隔符的组合（如 `("a","b:c")` 与 `("a:b","c")`）不会碰
  撞。
* 所有静态记录在所有查询时点均存在；时间只控制关联，不推断字段的历
  史修订或首次出现时间。

### links（0..30000 项）

每项恰含 `id, left, right, from_tick, to_tick`：

* `id` 沿用 `ident` 规则且在关联侧唯一；**重复 id 即使内容一致也拒
  绝**，不默默覆盖。
* `left, right` 各为恰含两个字符串的 JSON 数组 `[source, key]`，引用
  两条**不同的**现有记录；两端无方向性。
* `from_tick, to_tick` 为 0..10^12 的整数（拒绝 bool）且
  `from_tick < to_tick`。关联在且仅在 `from_tick <= t < to_tick` 时有
  效：`from_tick` 恰等于查询时刻生效，`to_tick` 恰等于查询时刻失效。
* 不同关联 id 允许覆盖相同记录对和重叠时段（平行关联），允许环，也
  允许关联两条来自同一来源的记录。

### queries（0..30000 项）

每项恰含 `id, record, at_tick`：

* `id` 沿用 `ident` 规则且在查询侧唯一；来源、关联、查询的 id 分属
  三个独立命名空间，文本相同互不解析。
* `record` 为现有记录键 `[source, key]`；`at_tick` 为 0..10^12 的整
  数（拒绝 bool）。
* 查询可以乱序，多个查询可以指向同一记录同一时点。

## 时点归并语义

对每个查询，取**该时点有效**的关联构成无向图，输出被查记录所在的完
整连通分量：

* `canonical_record`：分量内最小客户键 `[source, key]`，按 Python 字
  符串 `(source, key)` 元组字典序比较，**与来源 priority 无关**；它
  只是当前时点分量的确定代表，不是永久客户编号。
* `member_count`：分量内记录数（正整数）。每条记录只计一次：平行有
  效关联、环或重复覆盖同一记录对的关联都不增加计数；任意关联失效后
  只要还有有效路径（环中的替代路径、平行关联），仍属同一分量。
* 孤立记录的分量就是自身（`member_count = 1`）。

## 主数据治理语义

* **同源冲突**：分量内某 `source` 拥有至少两个不同 `key` 即冲突，即
  使这些记录的字段值完全相同。`conflict_sources` 是所有这类来源 id，
  按 Python 字符串顺序排列。冲突是正常业务结果（退出码 0），不意味
  着源 JSON 非法。
* **隔离**：分量含一个或多个冲突来源时整体隔离：`status =
  "quarantined"`、`fields = null`，不发布任何主字段，但仍输出准确的
  `canonical_record`、`member_count` 和全部冲突来源。
* **逐字段择一**：无冲突时 `status = "clean"`、`conflict_sources =
  []`，对 `display_name, email, phone` 各自独立地从非 null 成员值中
  按 `(priority, source, key)` 升序择一——不能只选一个整行赢家使其
  他来源的非空字段丢失；较优来源某字段为空时该字段落到次优来源。获
  胜值以 `{"value": ..., "record": [source, key]}` 发布，`record` 为
  该字段的血缘记录键；某字段全体成员均为 null 时该字段为 `null`。
* 一次桥接关联的生效或失效同时改变身份分量、来源冲突状态和受影响主
  字段及其血缘；隔离状态只属于对应时点，不污染分裂后的干净分量，已
  离开的成员也不再提供字段。

## 报告结构

顶层恰含 `schema_version, source_sha256, queries`：

* `schema_version` 恒为 1；`source_sha256` 覆盖源文件实际字节（小写
  十六进制）。
* `queries` 按查询 `id` 稳定排序，每项恰含 `id, at_tick, record,
  canonical_record, member_count, status, conflict_sources, fields`：
  * `record` 原样保留查询记录键 `[source, key]`；
  * `canonical_record` 为分量最小客户键数组 `[source, key]`；
  * `member_count` 为正整数；
  * `status` 恰为 `clean` 或 `quarantined`；
  * `conflict_sources` 为无重复、按 Python 字符串顺序排列的来源 id
    数组（clean 时为空）；
  * `fields` 在 quarantined 时为 `null`，否则恰含 `display_name,
    email, phone`，各值为 `null` 或 `{"value": ..., "record":
    [source, key]}` 对象。
* 报告不输出任意挑选的合并理由、匹配概率或永久客户编号。

## 算法与正确性论据

离线分治（时间段树 + 可回滚并查集），不逐 tick 展开、不为每个查询重
新扫描全部关联、不逐查询遍历成员分量：

1. **时间段树**：把所有不同查询时点（至多 30000 个）排序为叶子。每
   条关联的有效期 `[from_tick, to_tick)` 覆盖叶子的一个连续下标区
   间，被挂到该区间的 O(log Q) 个规范节点上；不覆盖任何查询时点的
   关联校验后不再参与计算。
2. **深度优先遍历**：进入节点时应用该节点全部关联，离开时逐一回
   滚。叶子处回答该时点的全部查询，此时并查集中恰好是该时点有效的
   关联集合——与查询顺序无关，每行都来自同一个准确时点状态。
3. **完整归并状态的保存与恢复**：并查集每个根携带分量的**完整治理
   摘要**——成员数、最小 `(source, key)`、按来源记录数字典、冲突位
   掩码（至多 64 个来源）、三个字段各自的获胜者 `(priority, source,
   key)`。每次 `union` 把恢复这些信息所需的全部旧值压入历史栈；
   `rollback` 精确撤销，使分裂后的两个分量恢复各自的成员数、最小
   键、来源计数、冲突集合与字段血缘，而**不只是恢复连通关系**。相
   邻时间分支（段树兄弟子树）从父节点的同一检查点出发，分支内应用
   的关联在返回前全部回滚，因此分支间完全隔离：一个分支里的合并
   （包括其造成的隔离状态与字段血缘）不会泄漏到另一分支。
4. **正确性**：叶子 `t` 的根路径上恰好是覆盖 `t` 的规范节点，即全
   体在 `t` 有效的关联，故分量正确；分量摘要的各类合并运算（min、
   计数求和、集合并、按全序取最小）都可交换可结合，与关联应用顺序
   无关，故摘要等于对分量成员直接计算的结果；回滚是应用的精确逆
   运算。
5. **复杂度**：设 L ≤ 30000 条关联、Q ≤ 30000 个查询、N ≤ 10000 条
   记录、S ≤ 64 个来源。每条关联被应用 O(log Q) 次，每次并查集合
   并/回滚为 O(S)（来源计数字典与冲突掩码），总时间
   O((L·log Q)·S + Q·(log N + S))，空间 O(N·S + L·log Q)。不按时
   间跨度（可达 10^12）展开。

## 确定性

* 记录按 `(source, key)` 排序后建立内部索引；分量摘要的合并运算与
  顺序无关；报告按查询 `id` 排序。
* 同一输入字节 → 报告字节完全一致（含 `source_sha256`）；输入数组
  重排后除 `source_sha256` 外报告逐字节一致。

## 错误行为

以下均为输入错误，退出码 2、不发布新报告（保留旧报告）：

* 顶层或对象字段缺失/多余、文档非对象、各数组越界（sources 为空或
  超 64、records 超 10000、links 超 30000、queries 超 30000）；
* 各类 id 非法或重复（重复关联 id 即使内容一致也拒绝）、`priority`
  或各 tick 越界、为 bool 或浮点；
* 记录引用未知来源、`(source, key)` 重复、字段值非 null 且不满足
  `ident` 规则；
* 关联端点不是恰含两个字符串的数组、引用不存在的记录、两端相同、
  `from_tick >= to_tick`；
* 查询引用不存在的记录；
* 重复 JSON 键、NaN/Infinity、超过 8 MB、输入输出同路径或硬链接、
  输出为符号链接。

## 测试

* `tests/identity_oracle.py` 是独立 oracle：对每个查询重新收集有效
  关联、用显式栈遍历连通分量，直接按契约文本计算规范键、成员数、冲
  突来源与逐字段获胜者；不导入 `queue_identity` 生产代码或其聚合帮
  助函数。oracle 只用于小例。
* `tests/test_identity.py` 用 oracle 比对全部小例与两组随机/交错实
  例，并覆盖：桥接前干净、桥接期间同源冲突、桥接失效后恢复（两侧字
  段赢家不同，逐行核对分量最小键、记录数、全部冲突来源、隔离与恢复
  后的字段值及血缘）；`from_tick`/`to_tick` 恰等于查询时刻的边界与
  同 tick 一关联失效另一关联生效；平行关联与环中替代路径在失效后不
  必分裂；跨来源相同 key 不混同、带分隔符的 source/key 组合不碰撞；
  priority 并列按 source 判胜；三个字段来自三个不同来源、较优来源
  字段为空、全字段为空与孤立记录；两个以上冲突来源、字段值完全相同
  的同源记录仍冲突；零关联、零查询、空 records、非法但未被查询的关
  联；输入重排稳定；非法结构与旧报告保留。
* 大例为可证明构造（`ScaleTest`）：64 来源、10000 记录、29996 条关
  联、30000 个查询、31 个不同查询时点。7500 条链上记录按相位交替成
  对（6 个相位，每相位一半边生效、另一半失效，交错切换），`[6W,
  7W)`（W = 10^9）窗口内全链 7500 条记录并成一个 64 来源全冲突的隔
  离分量，之后再次分裂为孤立记录；另 2500 条记录始终孤立。每个查询
  的分量由构造公式直接给出（对子/孤立/全链），字段血缘在至多 2 条
  记录间直接比较，不调用生产引擎。该规模下生产引擎一次求解约 1 秒，
  印证了不为每个查询重新扫描全部关联的复杂度论据。
* `fixtures/identity/source.json` 与
  `fixtures/identity/expected-report.json` 为自制合成样例：覆盖桥接
  隔离与恢复、边界生效/失效、平行关联、孤立记录、空字段与乱序重复
  时点查询；无真实客户数据。
